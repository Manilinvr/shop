# MANILI — пошаговая настройка

Всё, что нельзя сделать из кода: регистрации, договоры, ключи, кнопки в чужих
интерфейсах. Разделы независимы — магазин работает и без них, просто с
отключёнными возможностями.

**Порядок по важности.** Шаги 1–3 нужны, чтобы сайт открылся в интернете.
Шаги 4–6 — чтобы принимать деньги и отправлять заказы. Остальное — по мере
готовности.

## 1. Логотип и фотографии

### Логотип

1. Подготовьте файл логотипа в формате **SVG** (векторный, не картинка).
   Если есть только растр — подойдёт PNG с прозрачным фоном, шириной от 600 px.
2. Назовите его `manili-logo.svg` и положите в папку `public/brand/`.
3. Если есть кириллическая версия «Манили» — рядом как `manili-logo-ru.svg`.
4. Замените `public/favicon.svg` — это иконка вкладки браузера.

Сайт подхватит логотип сам, править код не нужно. Пока файла нет, в шапке
выводится нейтральная надпись MANILI без выдуманных знаков.

### Фотографии товаров

Загружаются прямо в админке: **Товары → выберите товар → Фотографии**.
Перетащите файлы или нажмите на область загрузки.

- Первый кадр — главный в каталоге, второй показывается при наведении
- Порядок меняется стрелками, лишнее удаляется корзиной
- До 8 кадров на товар, до 8 МБ каждый, JPG / PNG / WebP

**Важно:** до подключения Appwrite (шаг 4) фото хранится только в вашем
браузере — для примерки вида это нормально, но на другом устройстве его не
будет. После шага 4 файлы уходят в облако.

**Рекомендации по съёмке:** вертикальный кадр 3:4, ширина от 1600 px,
одинаковый фон и свет во всей серии.

## 2. GitHub Pages — сайт в интернете

**Уже настроено и работает:** https://manilinvr.github.io/shop/

Workflow сам переключает Pages в режим «GitHub Actions» при запуске, руками
лезть в настройки не нужно.

Каждый push в `main` публикует изменения автоматически. Запустить вручную:
**Actions** → *Deploy to GitHub Pages* → **Run workflow**.

### Если деплой падает: job `deploy` без шагов

Симптом: `build` зелёный, `deploy` красный, упал за пару секунд, логов нет
и в job не выделен runner. Это не ошибка сборки — окружение `github-pages`
отклонило запуск ещё до старта, потому что ветка не в списке разрешённых.

**Где чинится:** **Settings → Environments → github-pages** →
блок **Deployment branches and tags**.

Там либо выберите **All branches**, либо добавьте правило с именем `main`
(кнопка *Add deployment branch or tag rule*).

Важно: этот список **не обновляется сам** при смене основной ветки.
Если репозиторий начинал жизнь с другой веткой по умолчанию, в списке
останется её старое имя, и деплой с `main` будет молча отклоняться.

Заодно проверьте **Settings → General → Default branch** — там тоже
должна быть `main`.

### Если сайт открылся, но без стилей

Значит сборка не знает, в какой папке лежит сайт, и ищет стили не там.

Обычно это чинить не нужно: workflow определяет адрес сам. Есть файл
`public/CNAME` — публикуем в корень домена; нет — на страницу вида
`<логин>.github.io/<репозиторий>/`, и базовый путь подставляется
автоматически.

Перебить автоопределение можно переменной `VITE_BASE_PATH` в **Settings →
Secrets and variables → Actions → Variables**. Нужно это редко, и помните:
заданная вручную переменная побеждает автоматику, поэтому при подключении
домена её придётся убрать — иначе сайт останется в подпапке.

## 3. Домен manili-event.ru

Сейчас домен **не подключён** — сайт живёт на адресе GitHub. Этот шаг нужен,
только когда захотите свой адрес; до тех пор магазин работает полностью.

### В панели регистратора домена

Добавьте записи DNS:

| Тип | Имя | Значение |
|---|---|---|
| A | @ | 185.199.108.153 |
| A | @ | 185.199.109.153 |
| A | @ | 185.199.110.153 |
| A | @ | 185.199.111.153 |
| CNAME | www | `<ваш-логин>.github.io` |

### В GitHub

1. Создайте в папке `public/` файл с именем `CNAME` (без расширения),
   внутри одна строка — ваш домен:

   ```
   manili-event.ru
   ```

   Сборка увидит этот файл и сама переключит базовый путь с `/shop/`
   на корень домена. Подробнее — в `public/brand/DOMAIN.txt`.

2. **Settings → Pages → Custom domain** → впишите `manili-event.ru` →
   **Save**. Дождитесь зелёной галочки и поставьте **Enforce HTTPS**.

3. Если вы когда-то задавали `VITE_BASE_PATH` или `VITE_SITE_URL` вручную
   в Variables — удалите их, иначе они перебьют автоопределение.

DNS обновляется от 15 минут до суток. Пока не обновился, сайт доступен по
адресу `*.github.io`.

После переключения загляните в шаг 4.8: у функций в `SITE_URL` остался
старый адрес, на него возвращается покупатель после оплаты.

## 4. Appwrite — база данных и хранилище

Без этого шага данные живут только в браузере: заказ, сделанный покупателем,
вы не увидите.

### 4.1. Проект

1. Зарегистрируйтесь на [cloud.appwrite.io](https://cloud.appwrite.io)
2. **Create project** → название `MANILI`
3. Выберите регион (ближе к покупателям — Frankfurt)
4. Скопируйте **Project ID** из *Settings → General*

### 4.2. API-ключ

1. В левом меню **API Keys** → **Create API key**
   (в версиях постарше — *Overview → Integrations → API keys*)
2. Название: `manili-server`
3. Scopes — отметьте `.read` и `.write` у каждого из девяти:

   | Право | Зачем |
   |---|---|
   | `databases` | сама база |
   | `collections` | таблицы товаров, заказов, покупателей |
   | `attributes` | поля в них |
   | `indexes` | поиск и сортировка |
   | `documents` | записи: товары, заказы |
   | `files` | фотографии товаров |
   | `buckets` | хранилище под них |
   | `users` | покупатели и вход |
   | `functions` | загрузка серверных функций |

   Это девять строк — `functions` тоже обязателен, без него публикация
   функций отвалится с `missing scopes`.

4. Скопируйте ключ — **показывается один раз**

> Этот ключ даёт полный доступ к данным. Не отправляйте его в мессенджерах,
> не коммитьте в git, не вставляйте в поля с префиксом `VITE_`.
>
> Права можно поменять и позже, ключ пересоздавать не нужно:
> *API keys → ваш ключ → **Update***.

### 4.3. Что дальше: два пути

Дальше нужно создать в пустом проекте Appwrite таблицы под товары и заказы,
положить стартовое содержимое и поднять шесть серверных функций.

Всё это делают готовые скрипты из репозитория. Запустить их можно двумя
способами — результат одинаковый, выбирайте удобный.

**Путь А — кнопкой в браузере (рекомендую).** Ничего устанавливать не надо,
скрипты выполнятся на серверах GitHub. Дальше — шаги 4.4–4.5.

**Путь Б — на своём компьютере.** Нужен установленный Node.js и умение
открыть терминал. Описан в 4.6, на случай если захотите менять схему сами.

### 4.4. Сложить ключи в GitHub

Скриптам нужны три значения: адрес сервера Appwrite, ID проекта и API-ключ.
Ключ — секрет, остальное публично, поэтому кладём их в разные места.

Откройте репозиторий на GitHub → **Settings** → в левом меню
**Secrets and variables** → **Actions**.

Вкладка **Variables** → **New repository variable**, добавьте по очереди:

| Name | Value |
|---|---|
| `VITE_APPWRITE_ENDPOINT` | адрес из *Appwrite → Settings → General → API Endpoint*, вида `https://fra.cloud.appwrite.io/v1` |
| `VITE_APPWRITE_PROJECT_ID` | Project ID из шага 4.1 |
| `VITE_APPWRITE_DATABASE_ID` | `manili` |
| `VITE_APPWRITE_BUCKET_ID` | `media` |

Вкладка **Secrets** → **New repository secret**:

| Name | Value |
|---|---|
| `APPWRITE_API_KEY` | ключ из шага 4.2 |

> **Разница между вкладками важна, и ошибиться легко — поля выглядят
> одинаково.** Variables не шифруются: GitHub печатает их в журнале запуска
> как есть, а журнал публичного репозитория открыт всем. Кроме того, всё
> с префиксом `VITE_` вшивается в скрипты сайта и уезжает в браузер каждого
> посетителя. Secrets зашифрованы, в журнале заменяются звёздочками и
> обратно не читаются.
>
> API-ключ даёт полный доступ к вашим данным. Ему место **только** в Secrets.
>
> **Если ключ всё-таки побывал в Variables** — считайте его скомпрометированным.
> Выпустите в Appwrite новый (левое меню → **API Keys**), старый удалите,
> новый положите в Secrets. Удалить значение из уже записанного журнала
> нельзя, можно только удалить сам журнал — и это не отменяет того, что его
> могли прочитать.
>
> Оба workflow проверяют это перед работой и останавливаются, если в публичной
> переменной лежит что-то похожее на ключ.

### 4.5. Запустить настройку

Вкладка **Actions** → в левом списке **Настройка Appwrite** → справа кнопка
**Run workflow**.

В выпадающем списке **Что выполнить** оставьте **Всё сразу**. Галочку
«Добавить демо-товары» ставьте, только если хотите сначала посмотреть на
заполненный магазин, — в боевой базе эти товары придётся удалять руками.

Нажмите зелёную **Run workflow**. Через несколько секунд в списке появится
запуск, откройте его — видно, что происходит. Займёт 5–8 минут.

Что делает каждый шаг:

| Шаг в журнале | Что происходит |
|---|---|
| Проверить настройки | Сверяет, что все пять значений из 4.4 заданы. Если чего-то нет — пишет, чего именно, и останавливается, не трогая базу |
| Схема базы | Создаёт 17 коллекций с полями и индексами: товары, размеры, заказы, покупатели, промокоды, блоки главной |
| Стартовое содержимое | Наполняет категории, коллекции, блоки главной и два промокода-примера |
| Функции — сборка папок | Готовит шесть папок к публикации: у функций есть общий код, и его нужно положить в каждую |
| Функции — публикация | Загружает функции в Appwrite и запускает их сборку |

Повторный запуск безопасен: что уже создано — пропускается. Так что если
запуск оборвался на середине, просто запустите ещё раз.

**Если упало.** Откройте красный шаг — в конце будет текст ошибки.
`401` или `unauthorized` — неверный API-ключ либо ему не хватает прав из
шага 4.2. `404` или `project not found` — неверный Project ID или endpoint
другого региона. Поправьте значение в Settings и запустите workflow заново.

Если не получается только публикация функций, остальное уже сделано —
функции можно загрузить вручную, см. 4.7.

### 4.6. То же самое из терминала (необязательно)

Нужен [Node.js 22+](https://nodejs.org) и копия репозитория на компьютере:

```bash
git clone https://github.com/Manilinvr/shop.git
cd shop
npm install
```

Дальше три команды. Значения подставьте свои; обратный слэш в конце строки
означает «команда продолжается на следующей строке» — можно писать и одной
строкой, без слэшей.

```bash
APPWRITE_ENDPOINT=https://fra.cloud.appwrite.io/v1 \
APPWRITE_PROJECT_ID=вставьте_project_id \
APPWRITE_API_KEY=вставьте_ключ \
npm run setup:appwrite
```

```bash
APPWRITE_ENDPOINT=... APPWRITE_PROJECT_ID=... APPWRITE_API_KEY=... \
npm run seed:appwrite
```

Демо-товары — добавьте `-- --with-products` в конец второй команды.

```bash
npm run functions:build
npm install -g appwrite-cli
appwrite client --endpoint ... --project-id ... --key ...
appwrite push function --all --force
```

Project ID в `appwrite.config.json` менять не нужно: `appwrite client`
задаёт его сам.

### 4.7. Если функции не загрузились: вручную

Понадобится, только когда не сработал `appwrite push`. После
`npm run functions:build` в папке `build/functions/` лежат шесть готовых
папок. Для каждой:

1. *Functions → Create function → Manual*
2. Name и Function ID — как имя папки (`create-order` и т. д.)
3. Runtime: **Node.js 22**
4. Entrypoint: `src/main.js`
5. Build command: `npm install`
6. Заархивируйте **содержимое** папки в ZIP (сама папка внутрь архива
   попасть не должна) и загрузите в *Deployments*

**Права запуска** (*Settings → Execute access* каждой функции):

| Функция | Доступ | Почему |
|---|---|---|
| create-order | Any | Заказ оформляют и незарегистрированные покупатели |
| check-promocode | Any | Промокод проверяют до входа |
| quote-delivery | Any | Стоимость доставки считают в корзине |
| payment-webhook | Any | Вызывает банк, а не человек |
| telegram-webhook | Any | Вызывает Telegram, а не человек |
| set-order-status | **Users** | Меняет статус заказа — только вошедшие |

`payment-webhook` и `telegram-webhook` открыты для всех намеренно: их
вызывают внешние сервисы, которые не умеют входить в Appwrite. Подлинность
запроса проверяется подписью внутри самой функции — Appwrite тут не помощник.

### 4.8. Переменные функций

Функции живут отдельно от сайта и своих настроек не наследуют — каждой нужно
задать их самой. Это единственное место, где лежит API-ключ, кроме Secrets
в GitHub.

*Functions → выбрать функцию → Settings → Environment variables*. Всем шести:

```
APPWRITE_ENDPOINT      = https://fra.cloud.appwrite.io/v1
APPWRITE_PROJECT_ID    = ваш project id
APPWRITE_API_KEY       = ваш ключ
APPWRITE_DATABASE_ID   = manili
SITE_URL               = https://manilinvr.github.io/shop
```

`SITE_URL` — адрес, куда функция возвращает покупателя после оплаты.
Подключите домен — поменяйте здесь на него.

Остальные переменные (ключи банка, токен бота) — по мере подключения
сервисов, шаги 5–9.

### 4.9. Переключить сайт на Appwrite

Пока этого нет, сайт работает на демо-данных в браузере: заказ, оформленный
покупателем, вы не увидите.

**Settings → Secrets and variables → Actions → Variables**, добавьте:

```
VITE_BACKEND = appwrite
```

Остальные `VITE_APPWRITE_*` вы уже задали в 4.4.

Затем **Actions → Deploy to GitHub Pages → Run workflow**: сайт
пересоберётся с новой настройкой. Без этого шага изменение не применится —
значения вшиваются в сайт при сборке.

### 4.10. Разрешить сайту обращаться к Appwrite

Appwrite отвечает только тем адресам, которые вы перечислили сами, — иначе
браузер заблокирует запросы, и сайт будет молча пустым.

В левом меню **Apps** → кнопка **+ Add app** → **Web**.
В старых версиях консоли этот раздел называется *Settings → Platforms →
Add platform → Web app* — это одно и то же.

- Name: `MANILI`
- Hostname: `manilinvr.github.io`

Подключите домен — добавьте вторую платформу с ним.

### 4.11. Сделать себя администратором

Роль хранится в базе, а не в коде: сайту нельзя доверять то, что приходит
из браузера. Поэтому первого администратора назначают руками.

1. Откройте сайт → **Войти** → зарегистрируйтесь
2. В Appwrite: **Auth** → вкладка **Users** → найдите себя по почте →
   откройте → раздел **Labels** → добавьте метку `admin` → **Update**
3. Там же в *Databases → manili → profiles* найдите свой документ и
   поставьте `role` = `ADMIN` — это для отображения в админке
4. Обновите сайт с Ctrl+F5 — в меню появится **Админ-панель**

> Почему две записи, а не одна. Доступ к данным даёт **метка**, а не поле
> `role`: свой профиль человек правит сам (иначе не сменил бы имя или
> телефон), поэтому поле подделывается в два клика. Метку ставит только
> владелец проекта из консоли или сервер по API-ключу — на неё и опираются
> права всех коллекций. Поле `role` осталось для админки: по нему видно,
> кто есть кто, в списке покупателей.

## 5. Приём оплаты

Выберите одного провайдера.

|  | ЮKassa | Т-Банк |
|---|---|---|
| Комиссия | от 2,8% | от 2,3% |
| Подключение | 1–3 дня | 1–2 дня, быстрее со счётом в банке |
| Проверка webhook | обратный запрос к API | подпись в уведомлении |
| Самозанятым | да | да |

Оба адаптера уже написаны — разница только в том, какие переменные задать.

### 5.1. ЮKassa

1. [yookassa.ru](https://yookassa.ru) → **Подключить**
2. Заполните данные бизнеса (ИП / ООО / самозанятый), дождитесь проверки
3. *Настройки → Магазин* → скопируйте **shopId**
4. *Настройки → API ключи* → **Выпустить секретный ключ**
5. *Настройки → HTTP-уведомления*:
   - URL: адрес функции `payment-webhook` из консоли Appwrite
     (*Functions → payment-webhook → Domains*, вид
     `https://<id>.appwrite.global/`)
   - События: `payment.succeeded`, `payment.canceled`

Переменные для **всех** функций:

```
PAYMENT_PROVIDER = yookassa
PAYMENT_SHOP_ID  = ваш shopId
PAYMENT_SECRET   = ваш секретный ключ
```

Если подключена онлайн-касса, дополнительно:

```
PAYMENT_RECEIPTS = 1
PAYMENT_VAT_CODE = 1
```

`VAT_CODE`: 1 — без НДС, 2 — 0%, 3 — 10%, 4 — 20%.

### 5.2. Т-Банк

1. [tbank.ru/kassa](https://www.tbank.ru/kassa/) → **Подключить**
2. После проверки: *Магазины → ваш магазин → Терминалы*
3. Скопируйте **Terminal Key** и **Пароль**
4. *Настройки терминала → Уведомления → Notification URL* — адрес функции
   `payment-webhook`

```
PAYMENT_PROVIDER = tbank
PAYMENT_SHOP_ID  = ваш Terminal Key
PAYMENT_SECRET   = ваш пароль
```

### 5.3. Проверка

1. Включите тестовый терминал у провайдера
2. Оформите заказ на сайте
3. Оплатите тестовой картой (номера есть в документации провайдера)
4. Заказ в админке должен перейти в **Оплачен**, остаток — уменьшиться

Если статус не поменялся: *Functions → payment-webhook → Executions* —
там видно, дошло ли уведомление и что ответила функция.

> Пока `PAYMENT_PROVIDER` не задан, заказы создаются в статусе
> «Ожидает оплаты». Магазин работает, вы выставляете счёт вручную.

## 6. Доставка СДЭК

1. [cdek.ru](https://www.cdek.ru/ru/integration) → договор с интеграцией
2. В личном кабинете: *Настройки → Интеграция → API* → **Account** и **Secure password**
3. Узнайте код города отправления: *Интеграция → Справочники → Города*

Переменные:

```
DELIVERY_PROVIDER       = cdek
DELIVERY_ACCOUNT        = ваш Account
DELIVERY_API_KEY        = ваш Secure password
DELIVERY_FROM_CITY_CODE = код вашего города (Москва = 44)
```

**Без СДЭК** магазин считает доставку по вашим тарифам:

```
DELIVERY_PRICE_PVZ           = 35000   (350 ₽, значения в копейках)
DELIVERY_PRICE_COURIER       = 45000
DELIVERY_PRICE_POST          = 30000
DELIVERY_SELF_PICKUP_ADDRESS = Москва, ул. Примерная, 1
FREE_DELIVERY_THRESHOLD      = 1000000  (бесплатно от 10 000 ₽)
```

Суммы в копейках: 350 ₽ = 35000.

## 7. Telegram — уведомления о заказах

### 7.1. Бот

1. Откройте [@BotFather](https://t.me/BotFather) → `/newbot`
2. Имя: `MANILI заказы`, username: например `manili_orders_bot`
3. Скопируйте токен вида `1234567890:AAH...`
4. Откройте своего бота и нажмите **Start**

### 7.2. Узнать chat_id и привязать webhook

Придумайте секретную строку (любые 20+ символов) и выполните:

```bash
TELEGRAM_BOT_TOKEN=ваш_токен \
node scripts/register-telegram-webhook.mjs
```

Скрипт покажет ваш `chat_id`. Затем, подставив адрес функции
`telegram-webhook` из консоли Appwrite:

```bash
TELEGRAM_BOT_TOKEN=ваш_токен \
TELEGRAM_WEBHOOK_URL=https://<id>.appwrite.global/ \
TELEGRAM_WEBHOOK_SECRET=ваша_секретная_строка \
node scripts/register-telegram-webhook.mjs
```

### 7.3. Переменные

```
TELEGRAM_BOT_TOKEN      = токен от BotFather
TELEGRAM_OWNER_CHAT_ID  = chat_id из скрипта
TELEGRAM_WEBHOOK_SECRET = та же секретная строка
```

Теперь при каждом заказе придёт сообщение с составом, суммой и кнопками
**В работу / Готов к отправке / Заказ выполнен** — статус меняется прямо
из чата, заходить в админку не нужно.

Действия принимаются только из вашего чата: чужие нажатия отклоняются.

## 8. Email-уведомления

Подойдёт любой сервис транзакционной почты. Пример — Unisender Go
(российский, есть бесплатный тариф).

1. [go.unisender.ru](https://go.unisender.ru) → регистрация
2. Подтвердите домен отправителя (записи DKIM/SPF в DNS — сервис подскажет)
3. *Настройки → API* → скопируйте ключ

```
EMAIL_API_KEY   = ваш ключ
EMAIL_FROM      = orders@manili-event.ru
EMAIL_FROM_NAME = MANILI
EMAIL_OWNER     = ваша почта для копий заказов
```

Для другого сервиса (SendGrid, Resend, Mailgun) добавьте:

```
EMAIL_API_URL = адрес их API отправки
```

Формат запроса совместим с большинством; если нет — правится один `fetch`
в `functions/shared/notifications/email.js`.

Без этих переменных письма просто не отправляются, заказы работают.

## Если что-то не работает

| Симптом | Где смотреть |
|---|---|
| Сайт не открылся после деплоя | GitHub → Actions → лог workflow |
| Пустой каталог | Appwrite → Databases → products: есть ли записи со `status = PUBLISHED` |
| «Сервис временно недоступен» | Functions → нужная функция → Executions → лог |
| Оплата не подтверждается | Functions → payment-webhook → Executions |
| Браузер блокирует запросы | Appwrite → **Apps**: добавлен ли ваш адрес (в старых версиях — Settings → Platforms) |
| Нет доступа к админке | Auth → Users → вы → Labels: должна быть метка `admin` |
| Админка открылась, но всё пустое и с ошибками | Метки `admin` нет — есть только `role` в профиле. Добавьте метку |
| «Сборка остановлена: публичная переменная содержит не то» | В Variables лежит ключ вместо адреса. Разберите шаг 4.4 и выпустите новый ключ |
| `missing scopes` при публикации функций | Ключу не хватает прав. *API keys → ключ → Update*, отметьте `functions.read` и `functions.write` |
| Telegram молчит | `getWebhookInfo` покажет ошибку: запустите скрипт из шага 7.2 |

Логи функций Appwrite хранят только техническую информацию. Пароли,
данные карт и секретные ключи туда не пишутся.
